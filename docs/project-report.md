# Доклад по проекту Vitamins Backend (VitaInfo)

## 1. Описание предметной области

### 1.1. Назначение системы

Проект `Vitamins Backend` — это серверная платформа для мобильного приложения VitaInfo, предназначенного для поддержки регулярного и осознанного приема витаминов пользователями.

Основная практическая задача системы — перевести процесс «помнить о приеме витаминов и соблюдать схему» из ручного режима в управляемый цифровой сценарий:
- пользователь формирует персональные напоминания о приеме;
- система хранит структуру курса и расписание;
- система позволяет учитывать контекст приема (до/после/во время еды, дозировка, форма);
- система поддерживает доставку уведомлений по email для критичных пользовательских действий (например, восстановление/смена пароля);
- система собирает продуктовую аналитику для улучшения клиентского приложения и процессов.

### 1.2. Границы предметной области

Система покрывает следующие доменные зоны:

1. Учетные записи и доступ:
- регистрация и вход;
- работа с JWT-парами (access/refresh);
- управление профилем пользователя;
- безопасное восстановление и смена пароля через одноразовые коды.

2. Витаминный контур:
- справочник витаминов (`vitamin_catalog`) с базовыми атрибутами и контентом;
- пользовательские сущности напоминаний (`user_vitamins`), где фиксируются форма, доза, условие приема и заметки;
- курс приема (`vitamin_courses`) и расписание (`intake_schedules`, `intake_times`);
- настройки содержания уведомлений и переопределения текстов (`notification_preferences`, `notification_text_overrides`).

3. Аналитический контур:
- прием батчей событий от клиента;
- хранение событий с фильтрацией и экспортом;
- хранение и применение пользовательского consent на аналитику.

4. Коммуникационный контур:
- асинхронный воркер-нотификатор, который потребляет события из очереди и отправляет письма через SMTP.

Что явно не является бизнес-ядром предметной области:
- observability-стек (Prometheus, ELK) — это техническая эксплуатационная подсистема;
- CI/CD и инфраструктурные compose-профили — это контур разработки и сопровождения.

### 1.3. Основные участники (акторы)

1. Конечный пользователь мобильного приложения:
- создает и редактирует персональные напоминания;
- просматривает каталог и свой график;
- управляет согласием на аналитику;
- выполняет операции с аккаунтом.

2. Администратор/оператор продукта:
- выполняет экспорт аналитики через защищенный admin-эндпоинт.

3. Системные акторы:
- SMTP-провайдер (фактическая доставка писем);
- RabbitMQ (транспорт асинхронных событий);
- PostgreSQL/Redis (персистентность и краткоживущие токены/коды).

### 1.4. Ключевые бизнес-сущности и их смысл

1. Пользователь (`users`):
- идентичность, учетные данные, профиль;
- признаки consent для аналитики.

2. Каталог витаминов (`vitamin_catalog`):
- эталонные карточки витаминов/добавок;
- контентные поля для взаимодействий, совместимости, противопоказаний.

3. Пользовательское напоминание (`user_vitamins`):
- корневая сущность пользовательского плана приема;
- может ссылаться на позицию каталога или быть полностью пользовательской.

4. Курс (`vitamin_courses`) и расписание (`intake_schedules`, `intake_times`):
- задают период и конкретные моменты приема;
- поддерживают повседневный или кастомный график по дням недели.

5. Настройки уведомительного контента:
- флаги включения/исключения частей сообщения;
- пользовательские текстовые override для персонализации.

6. Аналитическое событие (`analytics_events`):
- атомарный факт поведения клиента во времени;
- может быть привязан к авторизованному пользователю (при consent) или анонимному идентификатору.

### 1.5. Базовые предметные правила

1. У каждого пользователя может быть много напоминаний, но каждая запись напоминания имеет не более одного курса и одного расписания.

2. Расписание хранится как комбинация:
- маска дней недели (`days_mask`);
- набор времен приема (`intake_times`) без дубликатов времени внутри одного расписания.

3. Условия приема и форма дозировки имеют нормализованные кодовые значения (например, `before_meal`, `after_meal`, `tablet`, `capsule` и т.д.), что обеспечивает единообразие данных между мобильным клиентом и сервером.

4. Сброс/смена пароля выполняются через одноразовые коды с TTL, ограничением попыток и rate-limit; промежуточные состояния хранятся в Redis.

5. Аналитика учитывает пользовательский consent:
- если пользователь авторизован, но не дал consent, события не связываются с `user_id`;
- при отсутствии и `user_id`, и `anonymous_id` событие считается некорректным.

6. Потоки доставки email асинхронны: бизнес-сервисы публикуют события, воркер выполняет отправку отдельно. Это снижает задержку пользовательских API-операций.

### 1.6. Типовые пользовательские сценарии в предметной области

1. Онбординг и первый план приема:
- пользователь регистрируется;
- выбирает витамин из каталога или задает собственный;
- настраивает курс, дни и время приема;
- получает персональный трек напоминаний.

2. Ежедневная эксплуатация:
- пользователь редактирует дозу/условия/заметки;
- временно отключает/включает напоминание;
- адаптирует контент уведомлений под личные предпочтения.

3. Безопасность доступа:
- при утере пароля пользователь проходит сброс через код;
- при изменении пароля в аккаунте проходит аналогичный двухшаговый сценарий подтверждения.

4. Продуктовая аналитика:
- клиент отправляет события пакетами;
- система сохраняет данные для анализа поведения и развития продукта;
- администратор экспортирует данные по фильтрам.

### 1.7. Ценность предметной области для продукта

Система решает сразу две прикладные задачи:
- повышает пользовательскую дисциплину приема витаминов за счет структурированного планирования и напоминаний;
- предоставляет продуктовой команде измеримую аналитику поведения, необходимую для принятия решений по развитию мобильного приложения.

Итогово предметная область проекта — это пересечение персонального health-planning (режим приема витаминов), безопасного account-management и data-driven сопровождения продукта.

## 3. Актуальность работы

### 3.1. Практическая актуальность для пользователей

Тема работы актуальна из-за повседневной проблемы соблюдения режима приема витаминов и пищевых добавок. На практике пользователи часто сталкиваются с несколькими трудностями одновременно:
- нерегулярность приема и пропуски;
- сложность удержания индивидуального графика в памяти;
- изменение схемы приема во времени (дозировка, время, условия до/после еды);
- необходимость быстро и безопасно восстановить доступ к аккаунту.

Проект решает эти проблемы в прикладной форме:
- переводит прием витаминов в структурируемый сценарий (курс, дни, время, условия);
- позволяет персонализировать напоминания под конкретного пользователя;
- поддерживает безопасные пользовательские операции (JWT, одноразовые коды, ограничение попыток, TTL, rate-limit).

### 3.2. Актуальность для продуктовой разработки

Современные цифровые продукты требуют решений на основе данных, а не только интуиции. Поэтому в проекте реализован отдельный аналитический контур:
- прием событий в batch-формате;
- фильтрация и экспорт данных;
- учет пользовательского consent на аналитику.

Это делает работу актуальной для реальной продуктовой эксплуатации:
- можно измерять поведение пользователей и качество пользовательских сценариев;
- можно проверять гипотезы по функциональности и интерфейсу;
- можно принимать обоснованные решения о развитии мобильного клиента.

### 3.3. Техническая актуальность

Работа актуальна и с инженерной точки зрения, поскольку отражает современный production-подход к backend-системам:
- микросервисная декомпозиция по бизнес-доменам (`gateway`, `auth`, `vitamins`, `analytics`, `notifier`);
- сочетание синхронного и асинхронного взаимодействия (gRPC + RabbitMQ);
- разделение долговременного и краткоживущего хранения (PostgreSQL + Redis);
- встроенная наблюдаемость (Prometheus/Grafana/Alertmanager, ELK);
- контейнеризированный запуск и воспроизводимая инфраструктура через Docker Compose.

Такой набор решений напрямую соответствует требованиям к надежности, поддерживаемости и масштабированию backend-платформ в 2026 году.

### 3.4. Значимость работы

Итоговая значимость проекта в том, что он одновременно:
- закрывает реальную пользовательскую задачу персонального health-planning;
- обеспечивает инженерно корректную основу для дальнейшего развития продукта;
- формирует учебно-практический пример полного цикла backend-разработки: от бизнес-домена и модели данных до observability и безопасной эксплуатации.

## 4. Цель и задачи работы

### 4.1. Цель работы

Цель работы — разработать и обосновать микросервисную backend-платформу для мобильного приложения VitaInfo, обеспечивающую персонализированное управление приемом витаминов, безопасную работу с пользовательскими аккаунтами и сбор аналитики для продуктового развития.

### 4.2. Задачи работы

Для достижения поставленной цели в проекте решаются следующие задачи:

1. Спроектировать предметную модель данных для хранения пользователей, справочника витаминов, персональных напоминаний, курсов, расписаний, настроек уведомлений и аналитических событий.

2. Реализовать контур аутентификации и управления профилем:
- регистрация, вход и обновление JWT-токенов;
- чтение и изменение профиля;
- безопасные сценарии сброса и смены пароля с одноразовыми кодами.

3. Реализовать бизнес-логику управления приемом витаминов:
- выдача каталога витаминов;
- создание, чтение, обновление, включение/выключение пользовательских напоминаний;
- хранение условий приема, формы, дозировки и расписания по дням/времени.

4. Реализовать аналитический контур:
- прием батчей событий от клиентского приложения;
- учет пользовательского consent на аналитику;
- экспорт аналитических данных для административных задач.

5. Реализовать асинхронный уведомительный контур:
- публикация доменных событий в брокер сообщений;
- обработка событий воркером и отправка email через SMTP без блокировки пользовательских API-запросов.

6. Обеспечить единый внешний API-вход через gateway и внутреннее межсервисное взаимодействие по gRPC.

7. Обеспечить эксплуатационную готовность системы:
- наблюдаемость (метрики, алерты, централизованные логи);
- контейнеризированный запуск полного стенда и воспроизводимость окружения.

8. Подготовить структуру проекта и документацию, достаточные для сопровождения, тестирования и дальнейшего расширения функциональности.

## 5. Требования к программному продукту

### 5.1. Функциональные требования

#### 5.1.1. Управление пользователями и доступом

1. Система должна обеспечивать регистрацию пользователя по email и паролю.
2. Система должна обеспечивать аутентификацию пользователя (вход) и выдачу пары JWT-токенов (`access` и `refresh`).
3. Система должна обеспечивать обновление токенов по `refresh token`.
4. Система должна предоставлять авторизованному пользователю доступ к своему профилю и возможность редактирования профиля.
5. Система должна поддерживать сценарий восстановления пароля:
- запрос кода;
- проверка кода;
- подтверждение нового пароля.
6. Система должна поддерживать сценарий смены пароля для авторизованного пользователя:
- запрос кода;
- проверка кода;
- подтверждение нового пароля.

#### 5.1.2. Управление витаминными напоминаниями

1. Система должна предоставлять API для получения каталога витаминов.
2. Система должна позволять создавать персональные напоминания о приеме витаминов.
3. Система должна позволять получать список напоминаний пользователя и детали конкретного напоминания.
4. Система должна позволять редактировать параметры напоминания:
- название;
- форму;
- дозу;
- условие приема;
- заметку;
- параметры курса и расписания;
- настройки контента уведомлений.
5. Система должна позволять включать и отключать напоминание без его удаления.

#### 5.1.3. Аналитика

1. Система должна принимать батчи аналитических событий от клиента.
2. Система должна хранить события в БД с учетом временных меток и атрибутов события.
3. Система должна учитывать пользовательское согласие на аналитику (`consent`).
4. Система должна предоставлять API для чтения и изменения статуса `consent`.
5. Система должна предоставлять административный экспорт аналитики по фильтрам.

#### 5.1.4. Асинхронные уведомления

1. Система должна публиковать события, связанные с паролями, в RabbitMQ.
2. Воркер уведомлений должен читать соответствующие события из очереди.
3. Воркер должен отправлять email через SMTP-провайдера.
4. Отправка уведомлений не должна блокировать пользовательские API-операции.

### 5.2. Нефункциональные требования

#### 5.2.1. Архитектурные требования

1. Продукт должен быть реализован как набор микросервисов с разделением ответственности по доменам.
2. Внешний вход в систему должен быть централизован через HTTP gateway.
3. Внутреннее межсервисное взаимодействие должно использовать gRPC.
4. Асинхронные процессы должны использовать брокер сообщений RabbitMQ.

#### 5.2.2. Требования к производительности и масштабированию

1. Система должна поддерживать пакетную обработку аналитических событий.
2. Сервисы должны быть развертываемы независимо друг от друга.
3. Архитектура должна допускать горизонтальное масштабирование stateless-компонентов.

#### 5.2.3. Требования к надежности

1. Долговременные данные должны храниться в PostgreSQL.
2. Краткоживущие данные (одноразовые коды, промежуточные токены, rate-limit ключи) должны храниться в Redis.
3. Для критичных связей данных должны использоваться ограничения целостности (PK/FK, unique, check).
4. Асинхронные операции должны быть отделены от синхронного клиентского потока.

#### 5.2.4. Требования к наблюдаемости

1. Система должна предоставлять технические эндпоинты проверки состояния (`/healthz`, `/readyz`) для сервисов.
2. Система должна предоставлять метрики Prometheus для основных сервисов API/бизнес-логики.
3. Система должна обеспечивать сбор инфраструктурных метрик (`postgres-exporter`, `redis-exporter`).
4. Система должна обеспечивать централизованный сбор логов в ELK-стек через GELF/Logstash.

### 5.3. Требования к безопасности

1. Доступ к пользовательским операциям должен выполняться только при валидном `access token`.
2. Доступ к административным операциям аналитики должен быть защищен `X-Admin-Token`.
3. Пароли пользователей должны храниться в виде криптографических хэшей (bcrypt), а не в открытом виде.
4. Сценарии сброса/смены пароля должны использовать одноразовые коды с ограниченным временем жизни.
5. Для сценариев подтверждения пароля должны применяться ограничения по числу попыток и частоте запросов.
6. Чувствительные операции должны выполняться с валидацией входных данных и корректной обработкой ошибок.

### 5.4. Требования к данным и БД

1. Модель данных должна включать сущности:
- пользователи;
- каталог витаминов;
- пользовательские напоминания;
- курсы и расписания;
- настройки уведомлений;
- аналитические события.
2. Для связей «один-ко-многим» и «один-к-одному» должны быть заданы соответствующие FK и уникальные ограничения.
3. Для сценариев удаления данных должны быть формализованы политики (`CASCADE`, `SET NULL`).
4. Для часто используемых запросов должны быть определены индексы (по пользователю, активности, времени события и т.д.).

### 5.5. Требования к развертыванию и сопровождению

1. Продукт должен запускаться в контейнеризированном окружении (Docker Compose).
2. Должны поддерживаться профили запуска:
- полный стек;
- только приложение;
- только инфраструктура.
3. Конфигурация должна задаваться переменными окружения (`.env`).
4. Проект должен содержать документацию по архитектуре, API и модели данных, достаточную для поддержки и развития решения.

## 6. Анализ существующих подходов и решений

### 6.1. Обзор аналогов

Для задач, связанных с режимом приема витаминов и добавок, в практике встречаются три типа решений.

1. Простые `reminder-only` приложения:
- фокус на локальных напоминаниях по времени;
- слабая или отсутствующая предметная модель курса;
- минимальная аналитика и ограниченные сценарии синхронизации.

2. Трекеры здоровья широкого профиля (универсальные habit/health приложения):
- поддерживают много типов активностей (вода, сон, питание, лекарства, витамины);
- дают гибкие шаблоны привычек, но не всегда глубоко моделируют предметные сущности именно витаминного приема;
- backend-слой часто ориентирован на общий `event-tracking`, а не на специализированную доменную структуру.

3. Медицинские/фармацевтические reminder-системы:
- сильный акцент на расписаниях и регулярности;
- часто более сложные UX и процессы, рассчитанные на медикаментозную терапию;
- повышенные требования к надежности и логированию, но нередко избыточная сложность для легкого wellness-сценария.

Вывод по аналогам: существует разрыв между «слишком простыми» напоминалками и «слишком тяжелыми» медицинскими системами. Проект VitaInfo занимает промежуточную нишу: специализированный, но не перегруженный функционал для витаминного контекста.

### 6.2. Сравнение подходов к построению backend-решения

#### Подход A: Монолитный backend

Преимущества:
- проще стартовая разработка и деплой;
- ниже порог вхождения для команды;
- меньше распределенных интеграций.

Ограничения:
- сложнее масштабировать отдельные подсистемы (например, аналитику и уведомления отдельно от API);
- выше связанность модулей;
- сложнее эволюционно менять контур без риска регрессий в соседних частях.

#### Подход B: Микросервисная архитектура

Преимущества:
- декомпозиция по бизнес-доменам (`gateway`, `auth`, `vitamins`, `analytics`, `notifier`);
- независимое развитие и масштабирование сервисов;
- естественная интеграция с асинхронными паттернами через брокер сообщений.

Ограничения:
- выше операционная сложность;
- больше требований к observability и дисциплине контрактов;
- дополнительная стоимость интеграционного тестирования.

Для данного проекта выбран подход B, так как он лучше соответствует структуре предметной области и требованиям к будущему развитию.

### 6.3. Сравнение способов межсервисного взаимодействия

1. REST между всеми сервисами:
- проще дебаг в начале;
- но увеличивает накладные расходы на межсервисные вызовы и дублирование HTTP-моделей.

2. gRPC между сервисами + HTTP только на внешнем edge:
- строгие контракты через `proto`;
- компактный бинарный формат и стабильная схема взаимодействия;
- удобное разделение: внешний API через `gateway`, внутренняя коммуникация через gRPC.

Выбран второй вариант: HTTP+JSON для клиентов и gRPC для внутренних сервисов.

### 6.4. Сравнение синхронной и асинхронной обработки

1. Полностью синхронный подход:
- проще трассировка одного запроса;
- но пользовательский запрос начинает зависеть от внешних каналов (например, email-сервиса).

2. Гибридный подход (sync + async):
- критичный пользовательский ответ отдается быстро;
- фоновые задачи (уведомления, ingest-потоки) выполняются через очередь;
- выше устойчивость при пиковых нагрузках и временных сбоях внешних интеграций.

В проекте выбран гибридный подход: синхронные API + асинхронный `notifier` и очередь событий.

### 6.5. Выбор используемых технологий, методов и архитектурных решений

Ниже приведено обоснование выбора ключевых решений проекта.

1. Go как основной язык backend:
- высокая производительность и предсказуемое потребление ресурсов;
- удобство разработки сетевых сервисов и конкурентных сценариев;
- зрелая экосистема для gRPC, метрик и инфраструктурной интеграции.

2. PostgreSQL как основная БД:
- надежная реляционная модель для доменно связанных сущностей;
- поддержка ограничений целостности (FK, unique, check), критичных для корректности расписаний и связей;
- JSONB-поля для гибких свойств аналитических событий.

3. Redis для временных состояний:
- низкая задержка операций;
- естественная модель хранения TTL-ключей (одноразовые коды, allowlist refresh-токенов, rate-limit).

4. RabbitMQ для асинхронных сценариев:
- надежная маршрутизация событий по routing key;
- развязка producer/consumer;
- возможность изолировать пользовательские API от задержек внешней email-инфраструктуры.

5. gRPC + Protocol Buffers для внутренних контрактов:
- строгая контрактная модель между сервисами;
- меньшие издержки сериализации/десериализации по сравнению с JSON на внутренних вызовах;
- удобство эволюции API по версиям proto.

6. Gateway-подход для внешнего API:
- единая точка входа для клиентов;
- единая политика аутентификации/авторизации и маршрутизации;
- упрощение клиентской интеграции и публикации Swagger-документации.

7. Наблюдаемость как обязательный архитектурный слой:
- Prometheus/Grafana/Alertmanager для метрик и сигналов состояния;
- ELK для централизованного анализа логов;
- отдельные health/readiness endpoints для эксплуатационного контроля.

8. Метод проектирования «домен + контракты + инфраструктурные гарантии»:
- сначала формализация бизнес-сущностей и правил данных;
- затем выделение сервисных границ и gRPC-контрактов;
- далее добавление эксплуатационного контура (метрики, логи, контейнеризация).

### 6.6. Итог сравнительного анализа

Выбранный набор решений (микросервисы, gRPC внутри, HTTP gateway снаружи, PostgreSQL + Redis + RabbitMQ, observability-стек) является обоснованным компромиссом между:
- функциональной глубиной предметной модели;
- масштабируемостью и поддерживаемостью;
- эксплуатационной готовностью и прозрачностью работы системы.

Для задач VitaInfo этот подход практически более устойчив и расширяем, чем упрощенный монолитный вариант, при приемлемом росте инженерной сложности.

## 7. Описание разработанных решений

### 7.1. Разработанная модель данных

В проекте реализована единая реляционная модель на PostgreSQL, разделенная на три доменных блока.

1. Блок учетных записей и доступа:
- `users` — хранение учетной записи, профиля и признака `analytics_consent`.

2. Блок витаминных напоминаний:
- `vitamin_catalog` — справочник витаминов;
- `user_vitamins` — пользовательское напоминание (корневая сущность);
- `vitamin_courses` — курс приема (one-to-one с `user_vitamins`);
- `intake_schedules` — тип и маска дней (one-to-one с курсом);
- `intake_times` — множество времен приема (one-to-many к расписанию);
- `notification_preferences` — флаги контента уведомлений (one-to-one к напоминанию);
- `notification_text_overrides` — пользовательские текстовые override (one-to-one к напоминанию).

3. Блок аналитики:
- `analytics_events` — поток событий с временными метками, контекстом сессии и JSONB-параметрами.

Ключевые особенности модели:
- строгая ссылочная целостность через FK;
- `ON DELETE CASCADE` для зависимых сущностей напоминаний;
- `ON DELETE SET NULL` для `analytics_events.user_id`;
- уникальные ограничения на one-to-one связи и на времена приема (`schedule_id + time_of_day`);
- индексы для пользовательских и аналитических выборок (`user_id`, `event_name`, `occurred_at`, `anonymous_id`).

### 7.2. Разработанные алгоритмы

#### 7.2.1. Алгоритм создания напоминания

Алгоритм реализован транзакционно в `vitamins-service`.

Шаги:
1. Валидация входа: `condition`, `form`, `timezone`, `start_date`, `end_date/duration`, `days`, `times`.
2. Разрешение источника названия:
- если передан `catalog_id`, сущность каталога читается из БД;
- если `name` пусто, берется `display_name` из каталога.
3. В одной транзакции создаются:
- `user_vitamins`;
- `vitamin_courses`;
- `intake_schedules`;
- набор `intake_times`;
- `notification_preferences`;
- upsert `notification_text_overrides`.
4. Возвращается агрегированная DTO-модель напоминания.

Результат: либо создается полностью консистентный набор сущностей, либо не создается ничего.

#### 7.2.2. Алгоритм обновления напоминания

Обновление выполняется как частичный patch в транзакции:
1. Проверка, что передано хотя бы одно изменяемое поле.
2. Чтение текущей версии напоминания и вычисление новых значений (merge).
3. Обновление базовых полей `user_vitamins`.
4. При переданном `course` — пересчет и обновление курса.
5. При переданном `schedule` — обновление маски дней и полная пересборка `intake_times`.
6. При переданных настройках уведомлений — merge/update `notification_preferences` и upsert overrides.
7. Повторное чтение и возврат итоговой модели.

#### 7.2.3. Алгоритм ingest аналитических событий

Алгоритм реализован в `analytics-service`:
1. Проверка batch-ограничений (`не пустой`, `<= 100 событий`).
2. Для каждого события:
- валидация `event_id`, `session_id`, `occurred_at`, `event_name`;
- нормализация/очистка `properties` с удалением PII-ключей;
- применение правила consent для `user_id`.
3. Проверка доменного инварианта: событие должно иметь `user_id` или `anonymous_id`.
4. Батч-вставка в БД с `ON CONFLICT (event_id) DO NOTHING`.
5. Расчет `accepted` и `deduplicated` по факту вставки.

Таким образом обеспечиваются идемпотентность по `event_id` и защита от повторной доставки одного и того же события.

#### 7.2.4. Алгоритм сброса/смены пароля

Сценарии построены как многошаговый протокол:
1. Генерация одноразового кода и хранение хэша кода в Redis с TTL.
2. Применение rate-limit и лимита попыток проверки кода.
3. При успешной проверке — выдача временного session-токена (Redis, TTL).
4. Подтверждение нового пароля по session-токену.
5. Отправка кода выполняется асинхронно через RabbitMQ + `notifier worker`.

### 7.3. Логика работы системы

#### 7.3.1. Логика на уровне сервисов

1. `gateway`:
- единая внешняя HTTP API-точка;
- аутентификация/авторизация (`Bearer JWT`, `X-Admin-Token`);
- маршрутизация запросов в соответствующие gRPC-сервисы;
- для analytics ingest может использовать publish в RabbitMQ.

2. `auth-service`:
- регистрация, логин, refresh;
- профиль пользователя;
- сценарии reset/change password;
- работа с Redis для временных ключей и allowlist refresh-токенов.

3. `vitamins-service`:
- справочник;
- полный CRUD жизненного цикла напоминания;
- кодирование и декодирование доменных значений (`condition`, `form`, `schedule`).

4. `analytics-service`:
- ingest и валидация событий;
- хранение consent;
- экспорт по фильтрам.

5. `notifier`:
- потребление событий email-уведомлений;
- отправка сообщений через SMTP.

#### 7.3.2. Логика взаимодействия компонентов

1. Синхронный контур:
- клиент -> `gateway` (HTTP/JSON) -> внутренние сервисы (gRPC).

2. Асинхронный контур:
- producer публикует событие в RabbitMQ;
- consumer обрабатывает событие независимо от клиентского запроса.

3. Контур хранения:
- PostgreSQL — транзакционные доменные данные и аналитические события;
- Redis — временные токены/коды/ограничители;
- RabbitMQ — межкомпонентные события.

4. Контур эксплуатации:
- health/readiness endpoints;
- метрики и алерты;
- централизованные логи ELK.

### 7.4. Принятые проектные решения и их эффект

1. Транзакционное формирование напоминания обеспечило целостность сложной агрегатной структуры (`user_vitamins + course + schedule + times + prefs`).

2. Разделение sync/async путей уменьшило задержку пользовательских API-операций и повысило устойчивость к сбоям SMTP.

3. Идемпотентный ingest аналитики через `ON CONFLICT DO NOTHING` упростил обработку повторной доставки событий.

4. Явная доменная валидация на уровне сервисов снизила риск накопления некачественных данных.

5. Наличие технического observability-контура повысило операционную прозрачность и упростило диагностику.

## 8. Выбор средств реализации

### 8.1. Язык программирования

В качестве основного языка выбран **Go (1.25)**.

Обоснование выбора:
- высокая производительность для сетевых backend-нагрузок;
- простой и предсказуемый concurrency-моделью (goroutines/channels), удобной для сервисной архитектуры;
- быстрый старт процессов и низкие накладные расходы в контейнерной среде;
- зрелая экосистема для gRPC, PostgreSQL, Redis, Prometheus и RabbitMQ;
- хорошая читаемость кода и сравнительно невысокая сложность сопровождения.

### 8.2. Фреймворки

1. **Gin** (`github.com/gin-gonic/gin`) — HTTP-слой в `gateway`:
- маршрутизация и middleware-пайплайн;
- обработка JSON-запросов/ответов;
- удобная интеграция со Swagger и метриками.

2. **gRPC** (`google.golang.org/grpc`) + **Protocol Buffers** (`google.golang.org/protobuf`) — внутренние сервисные контракты:
- строгая типизация и контрактность;
- компактный wire-формат;

## 9. Архитектура программы и особенности реализации

### 9.1. Общая архитектура системы

Система построена по микросервисной модели с разделением на функциональные домены и инфраструктурные контуры.

Архитектурные слои:

1. **Клиентский слой**:
- iOS-клиент и Swagger UI как потребители HTTP API.

2. **Edge-слой**:
- `gateway` как единая точка входа (`/api/v1`), выполняющая:
  - маршрутизацию;
  - проверку JWT;
  - проверку admin-доступа по `X-Admin-Token`;
  - преобразование HTTP-запросов в gRPC-вызовы.

3. **Слой доменных сервисов**:
- `auth-service` (доступ, профиль, reset/change password);
- `vitamins-service` (каталог и пользовательские напоминания);
- `analytics-service` (ingest событий, consent, экспорт);
- `notifier` (фоновый обработчик email-уведомлений).

4. **Слой хранения и событий**:
- PostgreSQL — транзакционные доменные данные и аналитика;
- Redis — временные ключи и ограничения;
- RabbitMQ — асинхронные события.

5. **Эксплуатационный слой**:
- Prometheus/Grafana/Alertmanager (метрики и алерты);
- ELK (централизованные логи).

Ключевой принцип архитектуры: синхронные пользовательские операции вынесены в gRPC-контур, а фоновые/внешние по задержке процессы (email, часть event ingest) вынесены в асинхронный контур RabbitMQ.

### 9.2. Взаимодействие сервисов

#### 9.2.1. Синхронные взаимодействия (HTTP + gRPC)

1. Клиент отправляет HTTP-запрос в `gateway`.
2. `gateway` применяет middleware авторизации/валидации.
3. `gateway` вызывает соответствующий gRPC-сервис:
- `auth-service` для auth/profile/password flows;
- `vitamins-service` для каталога и напоминаний;
- `analytics-service` для consent и экспорта.
4. Ответ gRPC преобразуется в JSON-ответ клиенту.

#### 9.2.2. Асинхронные взаимодействия (RabbitMQ)

1. **Password reset/change**:
- `auth-service` публикует событие `auth.password_*` в `vitamins.events`;
- `notifier` потребляет событие из очереди `notifications`;
- `notifier` отправляет email через SMTP.

2. **Analytics ingest (очередь)**:
- `gateway` (при включенном publisher) публикует `analytics.event`;
- `analytics-service` потребляет из очереди `analytics` и сохраняет в БД.

Таким образом достигается развязка по времени исполнения: пользовательский запрос не блокируется операциями отправки email.

#### 9.2.3. Взаимодействие с хранилищами

1. `auth-service`:
- PostgreSQL: пользователи и профиль;
- Redis: rate-limit, одноразовые коды, временные токены, allowlist refresh JTI.

2. `vitamins-service`:
- PostgreSQL: полный агрегат напоминания (root + course + schedule + times + preferences + overrides).

3. `analytics-service`:
- PostgreSQL: ingest, consent, экспорт событий;
- RabbitMQ (при соответствующем режиме ingest).

4. `notifier`:
- RabbitMQ + SMTP (без доменного хранилища состояния).

### 9.3. Диаграммы



### 9.4. Интересные технические решения

1. **Транзакционная сборка агрегата напоминания**:
- создание reminder выполняется в одной транзакции с записью в 6 связанных таблиц;
- гарантируется целостность всего агрегата.

2. **Patch-обновление сложной сущности**:
- частичный update с merge логикой для `course/schedule/preferences/overrides`;
- пересборка `intake_times` при изменении расписания.

3. **Параллельная агрегация при ListReminders**:
- сбор rich-response выполняется параллельно через `errgroup` с `SetLimit`;
- снижает латентность при большом числе напоминаний.

4. **Идемпотентный ingest аналитики**:
- вставка `ON CONFLICT (event_id) DO NOTHING`;
- корректный расчет `accepted/deduplicated` при повторной доставке.

5. **Санитизация аналитических данных**:
- фильтрация PII-ключей и redaction email-подобных значений в `properties`.

6. **Безопасный reset/change password протокол**:
- OTP-коды в виде hash в Redis;
- TTL, ограничение попыток, rate-limit;
- одноразовые промежуточные токены подтверждения.

7. **Контроль жизненного цикла refresh-токенов**:
- использование JTI allowlist в Redis;
- инвалидирование использованного refresh-токена при обмене.

8. **Гибрид sync/async архитектура**:
- HTTP/gRPC для интерактивных операций;
- RabbitMQ для операций, чувствительных к задержкам внешних систем.

9. **Структурированное логирование и операционные каналы**:
- JSON-логи через `slog`;
- разделение каналов (app/audit) и централизация в ELK.
